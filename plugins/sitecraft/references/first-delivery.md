# Quality before first delivery

Use for substantial creation or a new direction; a spacing fix needs only targeted checks. "First delivery" means the first working version handed to the user after internal QA. Do not describe a corrected result as an error-free first implementation. This protocol reduces generic defaults, without guaranteeing every outcome or classifying authorship.

## Before implementation

Briefly establish purpose, audience, primary journey and scope. Record connected decisions about composition, real content/images, type roles, palette, density and states. Preserve an existing identity. Do not ask the user to approve every routine choice inside requested scope.

Check the direction against the content:

- Would changing the name leave the same site usable for every industry? Find a difference derived from this product and its use, beyond a color change.
- What does the person see first and what can they do? A tool needs its workspace, a shop needs choice, and promotion needs a clear offer and action.
- Has the supposed alternative to generic AI styling become another preset: cream editorial, monochrome newspaper, acidic dark page or identical panels?
- Are information, visual materials and copy appropriate and truthful? Do not fill unknowns with invented reviews, metrics or decorative fake interfaces.

Correct mismatches before large implementation. Do not repeat answered questions. Consult [design rules](design-rules.md), [product profiles](product-patterns.md) and [official guidance](official-guidance.md) for specific decisions.

## Before handoff

Compare the actual result with its goal. Substantial products need observable [QA evidence](qa.md): main journey/result, important errors/recovery, persistence in the intended mode, wide/narrow layouts, keyboard controls, actual materials, overlap and Console checks.

| Quality | Evidence |
| --- | --- |
| Purpose and action | The target task is clear and completes in the stated mode |
| Individual character | Composition, content, type and materials belong to the product and do not copy a reference |
| Clarity and coherence | Copy, spacing, control roles and states agree across internal screens |
| Function and resilience | Data, errors, return, refresh and controls are checked within scope |

Do not assign an "AI percentage" or invented overall score. Fix material defects before handoff and retest affected paths. Complete independent work when an external service is blocked; identify the exact limit. Do not silently replace the requested product with a prototype.

## Evaluating the plugin

For realistic tasks, record request, instruction version, environment, actual inputs, initial implementation, findings and internal fixes. An independent evaluator receives the request and skill without the expected answer. Isolate fixtures from plugin source and user accounts. Label post-change reruns as reruns.

A sample count is not a guaranteed success probability. A screenshot supports only the viewed state; an interaction supports only its tested journey. Report packaging, behavior and visual findings separately. Improve instructions from observed failures, without adding a universal prohibition from one example. Recheck behavior after material instruction changes; a translated entrypoint is not independently re-evaluated merely because packaging passes.
